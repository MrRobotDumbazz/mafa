## Проблема

- Ручной просмотр записей — часы работы контролёра
- Часть нарушений **видима на видео**, но требует внимания человека к каждому кадру
- Банку нужен фильтр: показать проверяющему **конкретный фрагмент + основание**

**[0:15–0:40]** «Каждое видео — до 2,5 минут. Контролёр смотрит всё подряд. Наш сервис смотрит вместо него и поднимает флаг только там, где есть признак нарушения.»

---

## Решение — обязательный сценарий ТЗ (раздел 4)

1. Загружает .mov в веб-интерфейс (или через API)
2. Сервис анализирует → статус обработки
3. Вердикт: **нарушение не обнаружено / обнаружены признаки**
4. Каждое событие: **тип · таймкод · описание · кадр-доказательство · пункт НПА**

> Результат — подсказка для проверки человеком, не заключение (раздел 7 ТЗ)

**[0:40–1:00]** Проходит весь сценарий ТЗ от загрузки до нормативного источника.

## Архитектура — один процесс, ноль облака

```
веб-UI (React) → /web/api (маршрут сайта)
жюри-API (раздел 10) → /api/v1 (X-API-Key, 2 шага: analyze → jobs/{id})
        ↓
backend: чистый Python stdlib — очередь, 5-мин лимит, кадры через ffmpeg
        ↓
ML-пайплайн: YOLOv5n (люди) → трекинг → зоны
   + OWLv2 open-vocab (дверь/сейф/купюры/ключи/удостоверение)
   + RTMPose (запястья: пересчёт, передача)
   → rule-engine (действия ∨ клиент ∨ обстановка) → каталог НПА
```

**[2:00–2:50]** «Backend — на чистом stdlib, без единой внешней зависимости. Все модели локальные ONNX. Переносим во внутренний контур банка простым копированием.»

## Нормативная база — критерий 4 (15 баллов)

- **ПП НБРК от 29.11.2019 № 231** — основной (кассовые операции и инкассация)
- **ПП НБРК № 120** — справочно · **ПП НБРК № 58** — методологический (утратил силу — в ответы не идёт)
- **35 типов нарушений** с пунктами НПА (`services/ml/research/npa_analysis.md`)
- В ответ сервиса попадают **только verified-пункты** действующих актов — выдуманных ссылок нет (E8)

**[2:50–3:30]** «Каждое событие несёт документ и пункт. Мы сознательно не включаем акты, которых у нас нет в оригинале.»

## Метрики — честно (holdout, 13 видео)

| | значение | что это значит |
|---|---|---|
| **recall** | **1.00** | не пропустили **ни одного** нарушения (FAQ 16: «пропуск недопустим») |
| precision | 0.54 | часть чистых видео помечается — осознанный trade-off в пользу recall |
| тайминг | 173 с на 142-с видео | лимит ТЗ 300 с — с запасом |

Мы исследовали обратный trade-off: повышение precision режет recall до 0.33 — недопустимо по FAQ 16.

**[3:30–4:00]** Честно про метрики: полный recall, точность в приоритете развития.

## Инженерная устойчивость

- **Деградация:** без тяжёлых весов пайплайн падает на classic-режим (stdlib+ffmpeg) — сервис не падает никогда
- **Бюджет времени:** wall-clock guard 200 с + адаптивный интервал дорогих моделей
- **Контракты:** OpenAPI для жюри, JSON-Schema между зонами — фронт и бэк разрабатывались параллельно на моках

**[4:00–4:20]** Коротко про надёжность.

## Q&A — заготовки (2 минуты)

- **Почему precision низкий?** FAQ 16 требует нулевой пропуск — мы выбрали recall; показано исследование trade-off.
- **Как перенести в банк?** Копирование каталога + env с ключом; внешних вызовов нет (раздел 7 ТЗ).
- **Другой ракурс?** Детекции объектные + позы не привязаны к пикселям; геозоны относительные — частично устойчиво, проверяли на единственном доступном ракурсе.
- **Облако?** Нет: все модели ONNX локально; сеть нужна только чтобы один раз скачать веса.
